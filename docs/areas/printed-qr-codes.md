Moved out of the root `CLAUDE.md` in November 2026, word for word except where the pull request that moved it says otherwise. A section name in quotes ("Billing state", "Roles") is a heading in one of the files under `docs/areas/`; the index at the end of the root `CLAUDE.md` says which.

## Printed QR codes

A clinic prints a code on a pamphlet, a poster or its own handouts, and keeps it (Prompt 9; decisions by Evan on 2026-10-08). **The printed code is not a patient link: it hands one out.** Scanning it opens `/q/<code>`, the same calm page a patient link opens (`app/watch/PatientPage.tsx` draws both), and the patient's tap on Play makes a NEW link (a `Share`) for that one visit, with every rule a link has: 10 days after the first play (the settings), then paused, the renewals, the unclaimed days, never deleted. The printed code itself never runs out. Read the top of `lib/qr-code.ts` first.

- **One live code per procedure per surgeon per clinic**, printed or downloaded as often as the office likes (the same code every time). `QrCode.liveKey` is unique while a code is live, so five presses at once end with one code. Made with **Printed QR code** on `/admin/links` (`createQrCode()` in `lib/db/qr-codes.ts`): admins of an open clinic, the clinic from the session, the surgeon checked with Clerk (`resolveSender()`) and, under the same locks as `createShare()`, holding a seat here, and the clinic able to use the video. Logged in the clinic log, without the code.
- **Unguessable.** 25 characters from Node's cryptographic generator, about 128 bits; a clash on the unique column is tried again. The code is a secret like a key: never in a log, a log entry, a file name or an admin address (the admin pages use the row id).
- **The address is fixed on production**: `PERMANENT_QR_ORIGIN` in `lib/qr-code.ts`, `https://learn.pulse3dmedia.com`, never read from the request, because paper cannot be updated. It changes only on Evan's say-so, and changing it breaks every code ever printed. On a preview or a developer's computer the code carries that deployment's own trusted address (`qrOriginFor()`), and the pamphlet, the page and the downloaded file's name all say **Test only**. Never hand a preview printout to a patient. **A one-time patient link follows the same rule** (its address on `/admin/links` and in the library's Send panel, its QR picture and its pamphlet, which also says Test only away from production), so someone working on one of the production deployment's `*.vercel.app` addresses still gets the real address. With no address it can trust, a deployment makes no link: a phone on a developer's local network address gets none, and a local `next start` needs `APP_ORIGINS`.
- **Opening the page makes nothing.** GET `/q/<code>` reads the code and draws the page, with the "for education only" box and no playable address; a text-message preview, an email scanner, a crawler or a HEAD request leaves no link. Ticking the box posts to `/q/<code>/accept` (`app/q/[code]/accept/route.ts`), which checks the code as the page does and hands out the video, and **writes nothing**: there is no link to write on yet. Only the Play tap makes one: the player starts the video INSIDE the tap (phones allow sound only there) and at the same moment posts to `/q/<code>/issue` (`app/q/[code]/issue/route.ts`, POST only) with the visit's one-time key and the version of the words that were ticked (refused without one), and the new link is written with the tick's record already on it (first ticked at the Play tap's moment, one tick, that version; a retry of the same visit writes nothing more); the answer is the visit's link, and the address bar is changed to `/watch/<that code>` with `history.replaceState`, so a bookmark, a reload or a forwarded address is the patient's own link. No second tap, no screen in between.
- **A retry never makes a second link.** The link's code is worked out from the code's row id and the visit's key (`childShareCode()`, SHA-256, 16 characters, so it can never clash with a hand-made link's 10 or 6), so the same visit asking again finds its link, and five tries at once write one. The key is random (`crypto.randomUUID`), says nothing about the person or the phone, and is never stored. Two visits get two links.
- **Every tap is checked on the server, under locks** (`issueShareFromQrCode()`): the clinic's row, then the code's row (`lockQrCodeForIssue()`, FOR NO KEY UPDATE, so taps on one code take turns, which the daily limit needs; taps on different codes never wait for each other), then the video's, then the settings and the surgeon's seat. A retired code, a code that has handed out its daily limit, a closed clinic, a category off the plan, an unpublished video or a hidden placeholder hands out nothing, and the page says only "This video isn't available right now" with the clinic's number (one answer for all of them: nothing about billing or plans reaches a patient). A retirement that arrives while a link is being made waits for it (`lib/db/qr-codes.race.test.ts` proves it, with a control).
- **Retire and Replace**, on `/admin/links`, each after a popup. Retire (`retireQrCode()`) stops every printed copy at once and is never undone; Replace (`replaceQrCode()`) retires it and makes a new one for the same procedure and surgeon in one transaction, or changes nothing if the new one cannot be made. A link a code already handed out keeps working by its own rules after the code is retired, the category leaves the plan or the clinic closes, like every issued link.
- **The surgeon leaves or loses their seat** (decided by Evan on 2026-10-08): the code keeps working, and the links it hands out from then on name only the clinic (no surgeon id, no name). `/admin/links` marks the code "Needs a look" and offers Retire but not Replace (a new code would be in the same surgeon's name); the clinic makes a new code from a surgeon who holds a seat. The pamphlet then names only the clinic too.
- **Abuse.** Requests to `/q` count against the Vercel firewall rule (see "Security headers and link guessing"). **Each code hands out at most `qrDailyCap` links per UTC day** (200 by default, a setting on `/pulse/settings`, 1 to 10,000; decided by Evan on 2026-10-08 in Prompt M, replacing "a flag only, never a stop"): the count is taken under the code's row lock (`lockQrCodeForIssue()` counts as it locks), so two taps at once cannot both take the last place; past it, nothing is written and the patient sees the same "This video isn't available right now" page as any other refusal, until midnight UTC. A visit that already got its link still gets it back. Links already handed out keep working. A stored limit outside 1 to 10,000 is read as the default, never as no limit (`effectiveQrDailyCap()`). **The flag comes first, at `qrDailyFlag`** (100 by default, always below the limit; `qrDailyProblem()` in `lib/qr-code.ts` refuses a settings save that breaks that): Pulse staff only, on the clinic's `/pulse` page (which also says "At the daily limit") and in the list at the top of `/pulse`; nothing on the clinic side. **Pulse is emailed at both numbers** (audit finding F1, November 2026), because a photo of a poster can use up a code's day in about two minutes: the Play tap whose link makes the day's count EXACTLY `qrDailyFlag`, and the one that makes it exactly the limit, each send one email to `ERROR_ALERT_EMAIL` (`lib/qr-alert.ts`, through `lib/email.ts`; nothing is sent or looked up when email or that address is not set up). Which tap reached the number is decided inside the Play tap's transaction, where the count is already taken under the code's row lock (`qrDailyThreshold()` in `lib/qr-code.ts`; `issueShareFromQrCode()` hands back an `alert` of ids and numbers only), so one tap sees each number; the email also carries an idempotency key from the code's row id, the threshold and the UTC day (`qrAlertKey()`), so however many servers run, Resend sends it once. The route sends it after the answer has gone (`after()`, as `instrumentation.ts` does), so it never slows or fails the patient's Play, and a failed send is one log line with one word. The email names the clinic, the procedure and the count, with a link to the clinic's Links tab on `/pulse` built from an origin the deployment trusts (`pickTrustedOrigin()`); never the printed code, and nothing about whoever tapped. A retry of the visit that crossed the number gets its link back and no second email; if the server is stopped before the send, that email is lost (the flag is still on `/pulse`). **Lifting one code's limit for the day is not built**: the limit is one platform setting, so it needs a new column (proposed in the pull request that added the email); until then, raising "Printed-code links per day" on `/pulse/settings` takes effect at the next tap, for every code. No IP address, device or person is recorded anywhere.
- **Counted honestly.** The clinic side shows no numbers about codes (clinics get no usage numbers; see "The Pulse reports"). On the clinic's `/pulse` page each code shows the links it handed out today (UTC) and in the last 30 days (30 times 24 hours): links made by a tap on Play, not scans and not people. The reports count every link, these included; the overview's newest five leave them out.
- **Caching.** Both `/q/<code>` and the issue route are never cached (`force-dynamic`, `no-store`), carry `X-Robots-Tag: noindex` (`next.config.ts`), and nothing links to them or prefetches them.
- **What it does not protect against:** anyone holding the paper can watch that one procedure, which is what printing it is for. The links it hands out have the limits every link has (see "The video boundary").
