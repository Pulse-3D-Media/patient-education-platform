# The Pulse dashboard (`app/pulse`), the reports and the clinic log

Moved out of the root `CLAUDE.md` in November 2026, word for word except where the pull request that moved it says otherwise. A section name in quotes ("Billing state", "Roles") is a heading in one of the files under `docs/areas/`; the index at the end of the root `CLAUDE.md` says which.

## `app/pulse`, the Pulse 3D master dashboard

**`app/pulse` is the Pulse 3D master dashboard.** Used only by Pulse staff, Evan and Van. It shows every clinic, every video, and every price and rule. **Nothing on it is visible to clinics.** It is not a bigger `app/admin`: admin shows one clinic its own data, pulse sees across all of them, so the two never share a page.

**Who may open it is decided in one function, `isPulseStaff()` in `lib/pulse.ts`.** A person is Pulse staff when their Clerk user has `pulseStaff: true` in its public metadata, set by hand in the Clerk dashboard (Users, the user, Metadata, Public) and nowhere else. It is read on the server from Clerk's backend API on every request. **Every page and every Server Action under `app/pulse` calls `requirePulseStaff()` first**, which ends the request with not-found for anyone else: not a redirect, not a message, so the dashboard's existence is not confirmed to people who cannot use it. The `/pulse` layout checks too, so the not-found page has no dashboard rail around it. Never check this in the browser only.

**The demo site link.** The banner at the top of every `/pulse` page has "Open demo site", which opens the demo site in a new tab (`rel="noopener noreferrer"`). The demo site is a second copy of the app at a steady address (planned: `demo.pulse3dmedia.com`) on Stripe's test key, Clerk's test instance and the Neon `testing` branch, for sales calls: a standing showroom clinic, and a lead can be walked through signing up a new clinic and paying with Stripe's test card (decided 2026-11-18). The address comes from `DEMO_SITE_URL`, read on the server by `demoSiteUrl()` in `lib/demo-site.ts` inside the `/pulse` layout, after its staff check; it must be a plain `https:` address with no user name or password in it, and anything else counts as not set, when the link is simply not drawn. It is never taken from the browser and never appears on a clinic's screens. Demo clinics pile up on the demo side; `npm run db:clear-demo-clinics` clears them (see "The demo clean-up" under The database).

Built so far: the clinics table (`/pulse`, fifty clinics to a page, with "Printed QR codes flagged today" above it whenever a printed code at any clinic has reached the flag since midnight UTC, busiest first, at most twenty, each linked to its clinic's Links tab; `listFlaggedQrCodesToday()`), one clinic's page (`/pulse/clinics/[id]`, seven sections behind a row of pills: Overview with access set by hand, managed-by-Pulse, the read-only Card billing facts and the practice type, Plan, Details, Branding, People (with "Make account owner", the backup for an owner who left), Links (the clinic's printed QR codes, read-only, with the links each handed out today in UTC and in the last 30 days and the daily flag, then the newest twenty links with "From a printed code" on those a code handed out, and "Disclaimer accepted": when the "for education only" box was first ticked on each and how many ticks were recorded), and Notes, an append-only log to which every change saved on the page adds an entry of its own, shown fifty entries to a page, with a box for a new note that keeps what was typed until the server confirms the save; the clinics table flags a clinic with "No account owner"), the catalogue (`/pulse/videos`: every video, the add and edit form, and the Categories panel), the platform settings (`/pulse/settings`, where a number nothing reads yet would be marked "not active yet"; none is today) and pricing (`/pulse/pricing`: the numbers behind every quote, a live calculator, and the saved versions with Make active on each), and billing diagnostics (`/pulse/billing`: what became of each notification from Stripe, the ones that need attention first, and Try again on a failed one; never a key, a secret, an error message or what a notification contained). and reports (`/pulse/reports`, see "The Pulse reports" below).

## The Pulse reports

`/pulse/reports` shows Pulse staff, in totals, how links are made and played across every clinic, and `/pulse/reports/clinics/<id>` one clinic's. **Pulse staff only. Clinics get no reports or analytics at all for now** (decided by Van on 2026-10-08, after Evan's 2026-10-07 "not yet": numbers handed to a clinic could talk it out of renewing; revisited only if clinics ask). There is no Reports section on the clinic side, and `/admin/reports` only redirects to `/admin`. What each number means is at the top of `lib/reports.ts` and in a box on both pages; the words follow "Writing copy": a link is not a person, a play start is not a viewer or a watch.

- **A period is a group of links, not a diary.** 30 days (the default), 90 (`?days=90`), or two dates (`?from=2026-09-01&to=2026-09-30`, chosen on the page; whole days in Utah time, from midnight at the start of the first to midnight at the end of the last or now if sooner; a start before 2024, after the end or after today, or a date that cannot be read, falls back to the last 30 days with a sentence saying why; `readReportRange()` in `lib/reports.ts`): the links MADE in that window, with the plays and renewals recorded on them so far. A link made 31 days ago and played yesterday is not in "the last 30 days". The app keeps a running count on each link, not a dated record of each play, so activity per day cannot be worked out, and the page says so (decided by Evan on 2026-10-07).
- **The numbers:** links made; played (links with at least one play start); the played rate (played over made, a dash when nothing was made); play starts (`viewCount` summed); renewal requests (`Share.renewalRequests` summed: recorded taps on Ask my clinic, counted from October 2026, earlier ones were never kept); renewals (`renewalsUsed` summed). "Right now" numbers say so: clinics by status, open clinics' seats, and paused links waiting for their clinic (the same conditions as the overview's waiting list).
- **Seats** are counted for open clinics only (`clinicIsOpen()`), split by who provides them (`seatSourceOf()`): **Paid by card** (the clinic follows its own payments) and **Set up by Pulse** (managed by Pulse, or opened by hand). Seats in use are people plus open invitations, as on People. Every clinic's links count, open or not, managed or not.
- **Shown by** category, procedure (with the placeholder mark), clinic, and, on a clinic's page, surgeon (the name on their newest link in the period; links made before surgeons were recorded are one row).
- **Download CSV** above each table (category, procedure and clinic on the platform page; surgeon and procedure on a clinic's), for the same range, from `GET /pulse/reports/export` (`app/pulse/reports/export/route.ts`). Pulse staff only, checked in the route (anyone else gets a plain 404), never cached, at most 5,000 rows a file (`REPORT_EXPORT_LIMIT`). A file holds exactly what its table holds, under the same headings (`lib/report-csv.ts`): no link code, no Clerk id, nothing about a patient. A cell a spreadsheet would run as a formula (a clinic named "=...") is written as plain text, and the file opens cleanly in Excel (`lib/csv.ts`). The dates are in the file's name.
- **Bounded:** every number is counted in the database (`lib/db/reports.ts`), the clinic table is fifty to a page, and the procedure and surgeon lists stop at a hundred and say so. The index on `Share(clinicId, createdAt)` keeps the per-clinic counts quick.
- **What is never measured:** how far into a video anyone got (decided by Evan on 2026-10-07: nothing beyond the play start is reported from the patient's phone), anything about a patient, and no link code, signed address or patient link appears on a report.
- **Nothing in the app deletes a link** (`deleteShareForClinic()` exists, unused), so the counts cover every link ever made. If a way to withdraw a link is ever built, it must keep the row or the reports lose history.

**The clinic log.** `ClinicNote` is the history of a clinic as Pulse sees it: notes staff type (kind STAFF), and entries the app writes when something changes (kind STATUS, named for the first such change and shown as "Change"). **Every change staff save on a clinic's page writes an entry: access set by hand, plan, managed by Pulse, practice type, each detail field, and branding (including saves by clinic admins)**, saying what it was and what it became, under the staff member's name. Seats given and let go, invitations sent and revoked, and account owner changes are logged the same way (see "Surgeon seats"). The change and its entry go in one transaction (`changeClinicWithLog()` in `lib/db/clinics.ts`), so the current state and the history cannot disagree, and a save that changes nothing writes nothing. Entries are only ever added, with one exception: `npm run db:scrub-note-codes` (`prisma/scrub-note-codes.ts`, decided by Evan on 2026-11-16) rewrites the reactivation entries written before November 2026 so they name the link by its video and row id instead of its code (`lib/renewal-note.ts`), keeping everything else about them. Billing writes the same pair under the name "billing": one entry for each real change to a clinic's subscription, none for a repeated or late notification that changed nothing. If you add a new thing staff can change about a clinic, write it through the same helper so it is logged too. Nothing in the log is ever shown to the clinic.
