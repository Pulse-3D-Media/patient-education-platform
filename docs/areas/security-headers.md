# Security headers and link guessing

Moved out of the root `CLAUDE.md` in November 2026, word for word except where the pull request that moved it says otherwise. A section name in quotes ("Billing state", "Roles") is a heading in one of the files under `docs/areas/`; the index at the end of the root `CLAUDE.md` says which.

## Security headers and link guessing

- **Every response carries the same headers**, set in `next.config.ts` from `securityHeaders()` in `lib/security-headers.ts` (pure, worked out when a deployment is built; what each header is for is at the top of that file). Enforced today: no other site may frame our pages (`frame-ancestors 'none'` and `X-Frame-Options: DENY`), no plug-ins, no `<base>` trick, `Referrer-Policy: strict-origin-when-cross-origin` (another site is told our address, never the path, so a patient link's code never leaves), HSTS for two years without preload, `nosniff`, and no camera, microphone or location. No `X-Powered-By` header (`poweredByHeader: false` in `next.config.ts`). **A production build on Vercel stops** when `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` is missing or cannot be read (`checkClerkKeyForBuild()`), because the policy would otherwise let in every Clerk development instance; a preview, a developer's computer and the GitHub check (which has no settings at all) still build with that fallback.
- **The full content policy is enforced** (`Content-Security-Policy`, `CSP_ENFORCED` true since Evan's click-through of the PR #74 preview on 2026-10-27): the list of where scripts, styles, pictures, video and connections may come from (our own address, Clerk's address read from the publishable key, Clerk's bot check, the Webflow CDN for video, pictures only from the list in `lib/picture-hosts.ts`, Vercel's toolbar on previews only). The browser blocks anything outside the list and writes a line in its console. Before adding anything that loads from a new site (a script, a video host, a picture host, an outside service the browser calls), add the site to the list in `lib/security-headers.ts` and check the page on a preview with the console open; setting `CSP_ENFORCED` to false puts the policy back to report-only if something breaks.
- **Pictures come from a list** (Prompt S, October 2026): `PICTURE_HOSTS` in `lib/picture-hosts.ts`, read by the policy's `img-src` and by every box that takes a picture address. Today: the Webflow CDN (the starting category pictures, the animations and posters cut from them), `img.clerk.com` (every logo a clinic uploads on Branding, and staff pictures in Clerk's account menu) and `image.mux.com` (Mux stills), plus our own address and Clerk's. The logo box on a clinic's `/pulse` Branding tab, the poster box on `/pulse/videos` and the tile picture box in the Categories panel refuse an address on any other site with a sentence that says where it may live (`pictureHostRefusal()`). An address saved before the list existed is let through when it is sent back unchanged, so the rest of that form can still be saved; nothing stored was changed. Adding a site is one line in that file. Reading the testing branch in October 2026 found no stored logo, poster or tile picture at all, and video files only on the Webflow CDN; production was not read.
- **Cross-Origin-Opener-Policy: same-origin is enforced** (`COOP_ENFORCED` true, turned on with the content policy after Google sign-in was tried on the preview): a page of ours opened from another site is cut off from the page that opened it. `same-origin-allow-popups` is the fallback if a Clerk popup ever needs it.
- **Nonces instead of `'unsafe-inline'` for scripts: not yet, on purpose** (checked in Prompt S). Next.js puts a nonce on its own scripts only when the policy is set per request (in `proxy.ts`, alongside Clerk's middleware) and every page is drawn per request, so the static pages would stop being static and the policy would move out of `next.config.ts`. A change of its own, after the policy is enforced. **Once it is on, video plays only from the Webflow CDN and from Mux** (`stream.mux.com`, in `media-src` and, for hls.js's fetches, `connect-src`): a video added on `/pulse/videos` at any other address needs its host added to `media-src` first. Never set `Referrer-Policy` to `no-referrer`: the browser then sends `Origin: null` on our own Server Actions and Next.js refuses them, so every save on the staff side would stop working (the patient page has used routes since Prompt O, but the library, admin and `/pulse` forms are all Server Actions).
- **Link codes are ten characters** (lowercase letters and digits, `CODE_LENGTH` in `lib/db/shares.ts`), so guessing one at random is practically hopeless. Links made before October 2026 had six; codes shorter than ten are no longer accepted (`isAcceptedShareCode()` in `lib/share-link.ts`, asked first by every lookup behind the patient page that goes by the code alone), and are answered exactly like a code that does not exist: the calm not-found page, and nothing written. None was still working or paused when this was added (November 2026). Longer codes are accepted: a printed QR code's links have sixteen. A new code is not looked up before it is used: the unique column refuses one that is taken (Prisma `P2002`), and `createShare()` makes the whole attempt again with a new code, up to five times.
- **Guessing is also slowed at Vercel**, by one rate-limit rule in the project's Firewall (Hobby includes one), "Patient links and printed codes", published by Evan on 2026-10-08 (the `/watch` rule Prompt 7 described had never been added): Request Path **matches the expression `^/(watch|q)/`** (one condition on purpose: an OR of two conditions next to the rate limit's AND could be read as applying the limit to one path only and refusing the other outright), fixed window, 100 requests per 60 seconds, keyed by IP address, then Too Many Requests (429), which the printed-code page treats as "try again shortly". Checked the same day: a made-up `/watch` link answered 200 with the calm page, and 120 quick requests from one address got 98 answers and 22 refusals. A printed code's Play tap posts to `/q/<code>/issue`, and the "for education only" box posts to `/watch/<code>/accept` or `/q/<code>/accept`, each a route of its own rather than a Server Action, precisely so the public writes, and the request that hands out the video, always arrive at an address the rule covers. **The patient page has no Server Action at all** (Prompt O, October 2026): Next.js runs a Server Action by its id at ANY page address, so an action could be posted to `/` or `/sign-in`, which the rule does not watch. So the three calls a patient link's page makes once the video is on its way are routes too, each POST only, never cached, answering in plain JSON and logging only the kind of failure: the first real play, `/watch/<code>/play` (counts the play start and claims the first play once; on a Mux link it hands back a grant for the new deadline, only on a link with a recorded tick); a fresh signed address before the old one runs out, `/watch/<code>/refresh` (the link judged again, and only with a recorded tick); and Ask my clinic on a paused link, `/watch/<code>/ask` (one request per link per day, then the email). The browser's side is `app/watch/patient-calls.ts`; a test (`app/watch/[code]/patient-routes.test.ts`) fails if a `"use server"` line appears anywhere under `app/watch` or `app/q`. The staff side's Server Actions are unchanged: they can be posted at any address too, but every one of them checks who is signed in first. A patient's visit is a few requests, so a whole waiting room on one clinic Wi-Fi stays far below it. It is a live vendor setting, added and changed by Evan in the Vercel dashboard, never by code; Vercel's counters are per region, so it slows a script down rather than stopping one exactly.
