Moved out of the root `CLAUDE.md` in November 2026, word for word except where the pull request that moved it says otherwise. A section name in quotes ("Billing state", "Roles") is a heading in one of the files under `docs/areas/`; the index at the end of the root `CLAUDE.md` says which.

## Tests

`npm test` runs Vitest. Tests live next to the code they cover (`lib/db/clinics.test.ts` covers `lib/db/clinics.ts`; `lib/db/videos.test.ts` covers the catalogue; `app/pulse/actions.test.ts` covers the dashboard's actions; pure rules such as `lib/clinic-status.ts` and `lib/format.ts` get a plain test with no database) and hit a real database: the local test database on the developer's own computer for everyday runs, or the Neon branch called `testing` (both below). Whichever is used, its connection string is `TEST_DATABASE_URL` in `.env.test` (gitignored, like `.env`). `vitest.setup.ts` points Prisma at it, and **refuses to run unless it can show that is not production**: the decision is in `vitest.guard.ts` (which has its own tests) and it fails closed. The test string and every production string that is set must be readable, at least one production string must be set so there is something to compare against, and the test string may not name the same Neon endpoint as `DATABASE_URL` or `DIRECT_URL`, pooled or direct (Neon's `-pooler` address and the direct address of one endpoint count as the same database, and a port, a trailing dot or capitals on either side change nothing). That refusal is never bypassed, disabled or loosened to make a test run.

- **The local test database** (set up on Evan's computer on 2026-11-04). PostgreSQL 18, the version Neon runs, from the official Windows package (winget `PostgreSQL.PostgreSQL.18`, the server and command-line tools only), running as a Windows service that listens on this computer only (`listen_addresses = 'localhost'`, and its access list lets nothing else in). One database, `pulse_test`, owned by a login of the same name that is not an administrator; its password is in `.env.test` and nowhere else. **A full run takes about 2.5 minutes against it, against 25 to 35 against Neon**, because no query has to travel to Neon's servers in Ohio. `.env.test` holds both addresses with one switched off by a `#`: the local copy for everyday runs, and the Neon branch for a last full run before a release, because Neon is what the app runs on. The guard treats the local address like any other: plainly not production, so it passes, and the comparison still runs.
  - **It runs on UTC, as Neon does** (`ALTER DATABASE pulse_test SET timezone TO 'UTC'`). On the computer's own time zone, every time a hand-written query writes is hours off, and 17 tests fail.
  - **Rebuilding it:** make the login and the database, run `migrate deploy` with both strings pointed at it, then copy the Neon testing branch's rows across: `pg_dump --data-only --no-owner --no-privileges --exclude-table=_prisma_migrations` against the branch's direct address (this only reads Neon), loaded with `psql --single-transaction` after deleting the six `CategoryConfig` rows a migration makes. From then on the two databases drift apart, which does no harm: tests make and delete their own rows.
  - **A fast database finds what a slow one hides.** Two rows made one after the other can share a creation time to the millisecond, so a test that means "newer" sets the times itself (`lib/db/videos.test.ts` does).
- Tests must pass before any pull request that touches `lib/db`.
- **Tests create their own rows and delete them by id afterwards. They never touch, reset or overwrite rows they did not make.** A table with one shared row (AppSettings) is tested against an in-memory stand-in for the Prisma client instead (`lib/db/settings.test.ts`), because there is no row a test could call its own; a test that wants to see "the defaults" never deletes the real row to get them.
- `vitest.guard.test.ts` exercises the guard with **made-up connection strings only**. No test, log line or error message ever prints a real connection string, not even the rejected one; a refusal names the variable, never the value.
- `lib/pricing.test.ts` is the price fixtures, pure, and carries the record of the pricing decision. `lib/db/pricing.test.ts` hits the real testing database, and because only one version can be active in the whole table, it remembers which one was active when it started and makes it active again at the end. `lib/db/pricing.defaults.test.ts` uses an in-memory stand-in for the empty-installation and damaged-active-version cases, for the same reason the settings test does.

- **A full run against the Neon `testing` branch takes 25 to 35 minutes, and that is expected** (against the local test database it is about 2.5 minutes, see above; measured three times on 2026-11-02, with the testing branch to itself: about 1,850 tests, about 20,000 queries at about 70ms each, nearly all of the time spent waiting on the remote database, and the same tests slower at some hours than others). So one test or hook may take 60 seconds (`vitest.config.mts`), far above the slowest test's 28, and `vitest.setup.ts` gives a connection 15 seconds and a transaction 45 (the tests only: the app keeps its own limits, so a test passing does not show a transaction fits Prisma's 5 seconds). Never run two at once on the testing branch. **A test that hits a limit keeps running behind the next ones**, so its file's cleanup can run while it is still writing, and the rows it leaves (added or renamed categories above all) fail other tests. So do a run that is killed. Before reading a failure about categories as yours, look at the `CategoryConfig` rows.
